# 直播间语音播报

右侧「语音配置」只有一个自动播报总开关，在直播间连接且采集中生效。欢迎、介绍、报价、信息不足四个场景分别管理；每条录音都有播放器，可以暂停、继续、拖动进度或从头重听；手动播放和自动播报共用一个输出通道。估价匹配和语音调度彼此独立。

- **欢迎**：有新人进入时开始聚合。累计三人、期间累计三条评论，或等待约 30 秒，取同一个欢迎池的一条录音。两次欢迎至少间隔一分钟，过期不追播。
- **介绍**：有约 3 秒空档就从预制介绍中补一条；每轮打乱，轮内不重复。报价准备好后优先。介绍不阻塞报价生成。
- **报价**：收到真实成功的价格就开始生成，不等卡片动画。只念车系和实际区间，主句随机；正常报价约三分之一接独立预制的私信尾句。换车时，上一条未生成完成就取消；上一条主句已就绪或在播放则最多保留这一条，两辆都不再追加尾句。默认报价间隔为 7 秒，已手动保存的间隔不覆盖。模拟展示卡不发语音事件。
- **信息不足**：仅使用最终解析失败产生的七种语义原因；普通聊天、重复消息及系统异常不点名。昵称按可见字符取前 5 个后加“老板”，只影响声音。下拉选哪项，列表就只显示哪一类的录音；添加 WAV 或加入试听稿也归到该类。直播按留言实际命中的原因选录音，与界面正查看哪类无关。该类有录音才在本机合成称呼，接着播该类的一条；空类直接跳过。只在空档播，至少间隔一分钟，10 秒内没轮上就跳过。观众随后正常入队会撤销提醒。这不合并多条评论，也不改变入队规则。

## 合成调度与数据库

一个任务立即交给已预热的主路；主路忙且有其他独立任务等候才启动第二个工作进程。两路从同一队列取任务，先空先取，不凑对。第二路空闲后释放模型。报价优先、过期取消、播放单声道队列的规则不变。第二份模型需要额外内存；实际提速取决于设备和文本长度。

本地 `valuation.sqlite` 的 `voice_source` 只保留一个来源槽位，存储原始 WAV 字节、名称和选填原话；新上传成功才替换原记录。Base 的输入来自这一行，没有来源时提示上传，不把历史生成物当成参考。固定场景录音存于 `voice_scene_audio`，场景和条目对应关系在 `voice_catalog`。旧用户录音在首次迁移时读取，之后播放不再依赖原 WAV 路径。实时播报和未保存的试听稿留在内存。

校对稿可以用 `node scripts/generate-reviewed-voice.cjs --check 文件.md` 做纯文本核对，不调用模型。仅在确认校对稿、已上传声音来源、并且估价应用已退出时才运行同一脚本的 `--generate`。整批成功后事务写入，保留手动录音。

## 让观众听到

连接房间号是**收**评论，并不把本机音频**发**给观众。使用同一台电脑的抖音直播伴侣开播时，在伴侣的「直播设置 → 音频」选择和估价应用一致的扬声器设备。需要画面再单独采集估价窗口。先播放一条录音，看扬声器电平，并做一段本地测试录像检查；正式直播时使用同房间采集并打开自动播报。整台电脑声音被采集时，通知和手动试听也可能一起播出。若手机是实际推流设备，应将电脑音频送到手机的直播声卡输入，而不是只在电脑上连接那个房间。
